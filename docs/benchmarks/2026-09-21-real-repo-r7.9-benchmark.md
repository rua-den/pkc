## Release blocker discovered: transitive helper mutation over-promotion

The modern Angular benchmark exposed a wrong causality promotion in generated PO-facing knowledge.

`AppDbContext.SaveChangesAsync()` calls `SetTimestamps()`. `SetTimestamps()` iterates only tracked entries whose EF state is `Modified`, then conditionally updates either `User.UpdatedAt` or `Contact.UpdatedAt` depending on the runtime entity type.

Current feature-candidate traversal includes reachable helper conditions/mutations, and `GroundedKnowledgeSynthesizer.IsKnowledgeMutation(...)` promotes transitive member mutations without proving that the helper's mutated runtime object is actually the endpoint's affected entity.

This causes incorrect workflow claims such as:

```text
Auth Signup:
- Sets user.UpdatedAt to DateTime.UtcNow.
- Sets contact.UpdatedAt to DateTime.UtcNow.

Contacts Store:
- Sets user.UpdatedAt to DateTime.UtcNow.
- Sets contact.UpdatedAt to DateTime.UtcNow.
```

Those flows call `DbSet.Add(...)`, so the newly added entity is `Added`, not `Modified`; the timestamp helper does not perform those claimed mutations. The Contact Store path also does not modify the loaded current User.

The contamination is not isolated: both timestamp mutations are currently surfaced in 10 generated workflows each. Some update workflows legitimately modify one entity type, but the unrelated entity mutation is still over-promoted.

Classification:

```text
WRONG CLAIM / MUTATION-CAUSALITY LEAK
release blocker
```

This takes priority over adding broader R7.9 syntax support or beginning R7.10 implementation.

## Other useful benchmark findings

### Good fail-closed behavior

- PKC completed without crashing on all three pinned source trees.
- Unsupported modern Angular binding shapes did not create guessed R7.9 lineage.
- `jin12-xyz/CRM` did not manufacture entity→DTO→API lineage through unresolved DI/helper boundaries.
- `kesetovic/crm-system` did not claim frontend linkage merely because an Angular client exists.

### Product-comprehension gaps

- `jin12-xyz/CRM` knowledge misses the concrete per-user Contact filter because interface implementation/repository traversal is not resolved into the endpoint workflow.
- The Angular benchmark records the backend ownership predicate `c.OwnerId == user.Id` as observed-only evidence, but the PO-facing list workflow does not yet explain the practical result that non-superusers receive only their own contacts.
- Implementation-level success checks such as `if (await unitOfWork.CompleteAsync())` can appear as generic `Condition observed` business-rule prose. This is grounded but noisy and should not be confused with product policy.

## Release/demo implication

Do not claim real-repository R7.9 positive yield yet.

Near-term order:

```text
1. Regression-first reproduce the transitive helper mutation over-promotion.
2. Fix mutation causality generically without deleting independently useful lower-authority evidence.
3. Run focused + full existing gates.
4. Re-run this pinned real-repo benchmark and require the false timestamp claims to disappear.
5. Continue R7.10 only after the release blocker is closed.
6. Find or add one unchanged real repository that naturally yields the supported R7.9 chain for R7.14.
7. Run E knowledge-only PO acceptance.
```

Do not expand pre-demo scope into general DI resolution, AutoMapper support, Angular signals, observer-object subscriptions, collection item lineage, MCP, Azure DevOps, or runtime UI unless required to close a proven release blocker.
