## Findings

### F1 — P1: require value occurrence and path proof, not just declaration identity

Plan anchors: R7.1 at line 241, R7.2 at line 256, same-name negatives at lines 164-185 / R7.3.

The same-name negative compares distinct member declarations. It does not catch two receivers of the **same** declaration:

```text
productA.Price receives group.Price (100)
productB.Price already contains 99
service.Price receives productB.Price
```

Both assignments refer to the declaration `Product.Price`, but service received 99, not the value copied from group. Joining edges solely through `Product.Price` creates a false origin chain even though every individual assignment is real and semantically resolved.

A second negative must use fresh objects within one invocation and mutually exclusive branches:

```text
if flag: product.Price receives group.Price
else:    service.Price receives product.Price
```

There is no execution of that invocation in which the first write supplies the second read. Recording both conditional observations is valid; describing them as an established composed origin of the returned service is not.

**Required before A is green:** receiver/value-occurrence identity, compatible execution context, and write/read ordering sufficient for the supported shape. Add same-type distinct-instance, mutually exclusive branch, and overwritten-intermediate negatives. Where proof is incomplete, retain individual observed edges with their scope but do not compose an unconditional origin chain. A does not need a whole-program alias analyzer: it can support a narrow, proven straight-line shape and decline ambiguous compositions.

Do not confuse a graph of possible member transfers across the repository with provenance of a particular returned value. The portable wording must distinguish those two claims.

### F2 — P1: assignment syntax does not prove copy or snapshot semantics

Plan anchors: canonical semantics at lines 92-103, temporal example at lines 146-162, R7.4 at line 274.

An exact source/target property assignment can execute a custom getter, setter, conversion, or runtime-dispatched accessor. A setter that stores `value + 10` makes the resulting target a transformation, not an unchanged direct copy. A setter that ignores the write does not establish the proposed stored-value edge at all.

Similarly, assigning a mutable object reference copies the reference, not a frozen snapshot of its contents. Mutating the shared object later can change what the downstream reference observes without another downstream assignment. Distinguish the reference slot from the reachable object's state. The canonical decimal example is safe under a supported storage/accessor boundary; it does not justify classifying every property assignment as a value snapshot.

**Required before A is green:** a positive scalar/auto-property or equivalent proven storage fixture, paired with custom-setter and mutable-reference negatives. Either prove relevant accessor/conversion semantics or classify the stored-value/temporal conclusion as unproven while retaining the observed assignment. Add one actual dynamic-read fixture if A claims the advertised snapshot-versus-dynamic distinction; a single snapshot fixture does not demonstrate that distinction.

Snapshot wording must remain scoped: changing the upstream scalar alone does not alter this stored copy. It must not imply a repository-wide absence of later update jobs, events, mutations, or external writes. The plan correctly reserves later override explanation for B; A must avoid asserting its absence.

### F3 — P1: do not treat existing mutation metadata as exact project-backed lineage proof

Code anchors:

- `src/Pkc.CSharp/CSharpRepositoryScanner.cs:43`: a loose combined `PKC.RepositoryAnalysis` compilation is constructed from repository trees and platform references.
- `src/Pkc.CSharp/CSharpRepositoryScanner.cs:266`: assignments record a target display string and RHS syntax text, not a project-backed source-value identity.
- `src/Pkc.CSharp/CSharpProjectSemanticEnricher.cs:117`: project context labels are applied to facts in loaded files.
- `src/Pkc.CSharp/CSharpProjectSemanticEnricher.cs:125` and `:202`: mutation/initializer facts are not declaration-node enrichment targets; `semanticNodeMatch=not-applicable` returns the old payload with the new context labels.

Therefore `analysisMode=project-semantic` on a mutation fact does **not** establish that its assignment source and target have both been re-resolved and validated. Reusing its old `targetSymbol` or `value` as a proven edge would bypass the very boundary V0.4.7 needs.

**Required before A is green:** inspect the actual assignment operation in the target project's semantic model, resolve both ends and the relevant storage/conversion behavior, and attach the operation location plus proof context. Ambiguous/unresolved/error cases must not create a proven lineage edge. Test same-named declarations in distinct project/assembly contexts or another fixture that fails if display names substitute for semantic identity.

Existing fact identity and call summaries also need care when selecting the implementation design:

- `CSharpRepositoryScanner.CreateBehaviorFact` at line 415 uses path/start-line/kind/name; multiple same-target writes on one line are not separate value versions under that identity.
- `CSharpProjectSemanticEnricher.GetMethodTarget` at line 445 emits type + method name without overload signature; candidate lookup groups by that same form in `FeatureCandidateBuilder.cs:38`.
- Project model collection at `CSharpProjectSemanticEnricher.cs:365` keeps one model per file path. That does not by itself establish agreement across multiple compilation contexts for shared source.

Do not turn these existing summaries into lineage identity or cross-call proof. New lineage proof can be isolated and conservative; this review is not asking for an unrelated rewrite of all existing facts or a reopening of V0.4.6.

### F4 — P2: clarify that A must exercise retention and PO-readable output

Plan anchors: the portable acceptance requirement at line 86, R7.12 at line 346, and checkpoint A/E split at lines 394-417.

The plan already says raw facts are insufficient, but the sequence lists portable rendering in E. Make explicit whether that means final parity/polish or first availability. Treating A as accepted on raw edges alone would postpone discovery that the ordinary knowledge pipeline cannot carry the answer.

The current code has concrete integration boundaries:

- `FeatureCandidateBuilder.cs:10` whitelists behavior relation kinds; new lineage kinds are not automatically retained.
- Its behavior branch at line 77 adds the immediate target fact but does not recursively traverse a lineage graph.
- `ProductKnowledgeModel.cs:5` has existing rule/state/flow lists and flat evidence, with no existing structured lineage collection.
- `GroundedKnowledgeSynthesizer` constructs those existing sections; adding scanner facts alone does not add a lineage explanation.

**Required A delivery check:** one endpoint-backed canonical fixture must preserve both scoped edges through candidate building, synthesis, and workflow Markdown, with ordered source/target names, copy/snapshot semantics, and source traceability. Verify the false receiver/branch chains are absent from that same output. A dedicated field is one option, not a mandatory schema redesign; the representation must preserve meaning and stay distinct from business rules.

E can still own final folder/bundle/ZIP parity, blind PO review, and broader presentation acceptance. DTO/API/frontend work remains C/D. Define cycle/scope handling if lineage traversal is added, rather than blindly traversing every repository edge.

## Recommended first implementation contract

Keep the existing roadmap, but make A a deliberately small supported slice:

1. Compile and execute one fixture using scalar values, unambiguous member storage, and explicit supported call/receiver flow. It must show group 100 copied into product and service, then an upstream change to 120 leaving those copies at 100.
2. Scan that exact fixture and require two independently located, project-backed edges. Require its endpoint workflow to explain both the original chain and the immediate observed source for service.
3. Run adversarial negatives for distinct receivers, incompatible branches, intervening writes, setter effects, mutable-reference content, and unresolved semantic context. Unsupported cases may remain observations; they may not become proven composed/snapshot claims.
4. Require a separate dynamic-read positive or explicitly label dynamic support unfinished. Do not mark all of A complete on its first direct-copy subcheckpoint.
5. Retain independent lineage when a neighboring business predicate is observed-only. Do not store lineage in `contains-condition` or synthesize it as a business rule just to reuse rendering.
6. Review the chosen evidence/serialization semantics before changing any schema version. Do not bump package/schema numbers merely because the roadmap says V0.4.7.

Minimum proof payload, whether represented as facts/relations or an equivalent model:

```text
source member identity + receiver/value context
target member identity + receiver/value context
assignment/call scope and precise source span
transfer mechanism and its proof
temporal classification and its separate proof/unknown
composition eligibility / path qualification
authority retained independently from business conditions
```

This is a suggested proof boundary, not a demand to implement full alias analysis, path solving, persistence inference, or frontend composition in A.

## Validation and limits

This review inspected the current plan, permanent product contract, scanners, project semantic enrichment, fact identities, candidate traversal, synthesis, and portable models. A separate read-only Sol audit checked the retention and delivery boundary; the root reviewer evaluated and calibrated the findings above.

No production implementation or acceptance plan was changed during this review. The root reviewer inspected its source and independently ran its DLL: all seven assertions passed. The harness source is preserved below; generated files were removed. These are language-semantics/design checks, not failing PKC V0.4.7 regressions. The existing 88 C# / 13 frontend accepted results do not cover these new lineage gates. No new full-suite pass is claimed by this review.

## Conclusion

Proceed with V0.4.7, but turn F1-F3 into explicit regression requirements and resolve F4's delivery ambiguity before delegating a happy-path implementation. The target is a proven, portable explanation of a value's movement, not just a graph whose nodes have more qualified names.

Keep V0.4.6 closed. Keep V0.5 locked. These additions refine V0.4.7-A rather than expanding into the later milestones.

## Reproducible language-semantics harness

The following disposable .NET 10 console harness validates language semantics only. Its illustrative `Product` class is reused to create distinct objects; it is not a PKC analyzer fixture and its output makes no PKC production behavior claim. It uses no packages and disables apphost generation (`UseAppHost=false`); execute the resulting DLL with `dotnet <dll>`.

### `Program.cs`

```csharp
using System;

static class Program
{
    static int passed;
    static void Assert(bool condition, string name, string detail)
    {
        if (!condition) throw new InvalidOperationException($"FAIL: {name}: {detail}");
        passed++;
        Console.WriteLine($"PASS {passed}: {name} — {detail}");
    }

    static void Main()
    {
        var groupPath = RunBranch(groupToProduct: true);
        var servicePath = RunBranch(groupToProduct: false);
        Assert(groupPath.ProductPrice == 100m && groupPath.ServicePrice == 0m,
            "branch-exclusive Group→Product", "Product receives Group.Price; Service remains untouched");
        Assert(servicePath.ProductPrice == 0m && servicePath.ServicePrice == 0m,
            "branch-exclusive Product→Service", "Product has no upstream value, so Service receives 0");
        Assert(servicePath.ServicePrice != 100m,
            "branches cannot compose", "a union graph may suggest Group→Product→Service, but no call executes both writes");

        var group = new Product(100m);
        var productA = new Product(10m);
        var productB = new Product(99m);
        productA.Price = group.Price;
        var servicePrice = productB.Price;
        Assert(productA.Price == 100m && servicePrice == 99m,
            "instance-sensitive Product.Price", "Product.Price on A and B are distinct locations despite the same symbol");
        Assert(!ReferenceEquals(productA, productB),
            "same symbol, distinct instances", "symbol equality cannot establish object identity or transitivity");

        var source = new PlainPrice { Price = 5m };
        var target = new AdjustedPrice();
        target.Price = source.Price;
        Assert(target.Price == 15m && target.Price != source.Price,
            "custom setter", "target.Price = source.Price stores source + 10");

        var sourceBox = new Box { Payload = new MutablePayload { Value = 1 } };
        var targetBox = new Box { Payload = new MutablePayload { Value = 0 } };
        targetBox.Payload = sourceBox.Payload;
        sourceBox.Payload.Value = 7;
        Assert(targetBox.Payload.Value == 7,
            "mutable reference alias", "assignment preserves reference identity");

        Console.WriteLine($"ALL {passed} ASSERTIONS PASSED");
    }

    static (decimal ProductPrice, decimal ServicePrice) RunBranch(bool groupToProduct)
    {
        var group = new Product(100m);
        var product = new Product(0m);
        var service = new Product(0m);
        if (groupToProduct)
            product.Price = group.Price;
        else
            service.Price = product.Price;
        return (product.Price, service.Price);
    }

    sealed class Product(decimal price)
    {
        public decimal Price { get; set; } = price;
    }
    sealed class PlainPrice { public decimal Price { get; set; } }
    sealed class AdjustedPrice
    {
        decimal stored;
        public decimal Price { get => stored; set => stored = value + 10m; }
    }
    sealed class Box { public MutablePayload Payload { get; set; } = new(); }
    sealed class MutablePayload { public int Value { get; set; } }
}
```
