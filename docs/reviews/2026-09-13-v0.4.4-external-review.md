## Blocker 1 — validation correlation can false-positive `consistent`

Classification:

```text
wrong claim
uncertainty/authority overclaim
```

Current condition comparison can reduce compound conditions to a single equality key. If both sides share that one equality but one side contains additional predicates, PKC can incorrectly classify the requirements as equivalent.

Example risk:

```text
UI required when:
serviceType == CSP && region == US

backend required when:
serviceType == CSP
```

A lossy normalized key such as:

```text
servicetype=csp
```

must not be sufficient to emit:

```text
consistent
```

or raise the comparison to high confidence.

### Required fix

- Preserve the full condition semantics that PKC can prove.
- If condition equivalence cannot be proven deterministically, classify conservatively as `possible-mismatch` or `unknown` rather than `consistent`.
- Do not silently upgrade lossy normalization to high confidence.
- Add regression coverage for compound conditions, reversed operands, mixed conditional/unconditional requiredness, and multiple requiredness facts.

## Blocker 2 — repeated builds can leave stale files in canonical `knowledge/`

Classification:

```text
handoff/packaging mismatch
wrong claim risk
```

`pkc build` currently writes the files discovered in the current build but does not reconcile/delete generated knowledge files that existed in a previous build and are no longer generated.

Risk scenario:

```text
build #1
endpoint A exists
→ knowledge/workflows/orders/a.md generated

source changes
endpoint A removed

build #2
→ current bundle and ZIP omit A
→ stale knowledge/workflows/orders/a.md can remain on disk
```

This violates the contract that `knowledge/` is canonical and transport must not change meaning. A PO providing the structured folder could expose obsolete behavior that is absent from `PKC_KNOWLEDGE.md` and `PKC_KNOWLEDGE.zip`.

### Required fix

- Reconcile generated `knowledge/` atomically or explicitly delete obsolete generated files before publishing the new canonical pack.
- Do not delete unrelated user-owned files unless PKC has a clear generated-file ownership rule.
- Add an end-to-end repeated-build regression: build once, remove an endpoint/source capability, build again, and prove the obsolete workflow/feature disappears from `knowledge/`, bundle, and ZIP.

## Blocker 3 — capability-flow scoring is Loren-shaped

Classification:

```text
benchmark gaming / overfit risk
comprehension generalization risk
```

The current product-flow ranking explicitly boosts symbols containing names such as:

```text
IAction
IBrain
IMemory
IProject
```

and prioritizes boundary suffixes including:

```text
Brain
Loop
Catalog
Builder
Collector
```

Several of these are strongly aligned with Loren's architecture and the regression fixture repeats the same terminology.

Because scoring occurs before the feature-level flow cap, lexical preferences can decide which edges survive into product knowledge.

### Required fix

- Prefer repository-neutral structural signals such as endpoint distance, interface/cross-component boundary, graph role, cross-project/application-layer transition, or other deterministic semantic evidence.
- If lexical role hints remain, make them generic and prove them using neutral fixtures that do not reuse Loren terminology.
- Add tests using materially different names such as `ExecutionCoordinator`, `ContextProvider`, `ConversationRepository`, `UseCase`, or equivalent neutral boundaries.

## Blocker 4 — frontend source scope can ingest tests/spikes

Classification:

```text
wrong claim
source contamination
```

C# product scanning excludes conventional product-non-source directories such as:

```text
test
tests
spikes
```

The frontend scanners do not currently apply the same product-source scope consistently. Angular/React scanning can therefore ingest frontend test/spike files, including common files such as `*.spec.ts` / `*.test.ts`, and those facts can be linked to production endpoints.

The pinned Loren acceptance proving no test/spike contamination on that repository does not prove the frontend rule generically.

### Required fix

- Introduce a shared or equivalent explicit frontend product-source scope.
- Exclude conventional test/spike directories and conventional test files where appropriate.
- Add regression coverage where a test component/test file calls the same production endpoint and prove it does not contaminate portable product knowledge.

## Warning 1 — portable evidence loses per-fact confidence/provenance

Classification:

```text
traceability gap
```

Raw evidence records analyzer fidelity such as `analysisMode`, `analysisConfidence`, and fallback reasons. The portable `KnowledgeEvidence` representation currently preserves source location and description but not those per-fact fidelity fields.

Workflow-level fallback warnings are useful and prevent this from being a blocker by itself, but the portable evidence layer does not yet fully satisfy the stronger contract of claim-level provenance/confidence.

Recommended follow-up: preserve compact analyzer mode/confidence/caveat metadata per important evidence item without flooding product-level pages.

## Warning 2 — blind-review record is not fully reproducible as durable evidence

Classification:

```text
benchmark evidence gap
```

The blind-review procedure is sound: source hidden first, answers frozen, source cross-check later, and CI alone cannot pass the gate.

However, the committed record would be stronger if it preserved enough durable information to reproduce the exact review, for example:

```text
generated bundle/artifact hash
workflow/run identifier
reviewer/model configuration
fixed question → frozen answer transcript
source cross-check result per question
structured-pack parity answer/check
```

This is not a blocker for the compiler implementation, but should be improved before relying heavily on blind-review history as release evidence.
