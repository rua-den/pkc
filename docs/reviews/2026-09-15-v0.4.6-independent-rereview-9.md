## Remaining B6.4 blocker — unproven `IQueryProvider` semantics

The business-predicate pipeline accepts both exact `System.Linq.Enumerable.*` and exact `System.Linq.Queryable.*` operation targets as supported authority candidates.

`CSharpBusinessPredicateEnricher.TryResolveSupportedOperation()` recognizes either `Enumerable.<operation>` or `Queryable.<operation>`.

`CSharpBusinessPredicateAuthorityFilter.IsSupportedTarget()` likewise accepts either family.

The observable `Where` preservation proof then checks the syntax/semantic path from the `Where` invocation to the returned expression, but it never proves the runtime semantics of `IQueryable.Provider`.

This is insufficient for `Queryable.Where`.

The .NET contract is provider-mediated: `Queryable.Where` constructs a `MethodCallExpression` and passes it to `source.Provider.CreateQuery(...)`. The resulting runtime behavior depends on the implementation of the source/provider. Filtering by the predicate is the expected behavior, but it is not established merely from resolving the call to `System.Linq.Queryable.Where`.

### Smallest behavior-valid counterexample shape

```csharp
using System.Collections;
using System.Linq.Expressions;

public sealed class Card
{
    public bool IsPublished { get; set; }
}

public sealed class IgnoringQuery<T> : IQueryable<T>, IQueryProvider
{
    private readonly IReadOnlyList<T> _items;

    public IgnoringQuery(IEnumerable<T> items)
        : this(items.ToArray(), null)
    {
    }

    private IgnoringQuery(IReadOnlyList<T> items, Expression? expression)
    {
        _items = items;
        Expression = expression ?? System.Linq.Expressions.Expression.Constant(this);
    }

    public Type ElementType => typeof(T);
    public Expression Expression { get; }
    public IQueryProvider Provider => this;

    public IEnumerator<T> GetEnumerator() => _items.GetEnumerator();
    IEnumerator IEnumerable.GetEnumerator() => GetEnumerator();

    public IQueryable CreateQuery(Expression expression) =>
        new IgnoringQuery<T>(_items, expression);

    public IQueryable<TElement> CreateQuery<TElement>(Expression expression)
    {
        if (typeof(TElement) != typeof(T))
        {
            throw new NotSupportedException();
        }

        return (IQueryable<TElement>)(object)new IgnoringQuery<T>(_items, expression);
    }

    public object? Execute(Expression expression) => throw new NotSupportedException();
    public TResult Execute<TResult>(Expression expression) => throw new NotSupportedException();
}

private readonly IQueryable<Card> _cards =
    new IgnoringQuery<Card>(
    [
        new Card { IsPublished = false }
    ]);

public IReadOnlyList<Card> GetCards() =>
    _cards
        .Where(card => card.IsPublished)
        .ToList();
```

The provider keeps the expression tree for query identity but intentionally enumerates the underlying items without interpreting the `Where` expression.

Observable behavior:

```text
source item has IsPublished == false
→ Queryable.Where builds an expression and delegates to Provider.CreateQuery
→ provider returns a query carrying that expression
→ Enumerable.ToList enumerates the provider-backed query
→ provider yields the false item without applying the predicate
→ returned list contains an item that does not satisfy card.IsPublished
```

The current PKC authority path can still see:

```text
exact target: System.Linq.Queryable.Where
→ supported business predicate
→ observable returned value path
→ Enumerable.ToList accepted as callback-free materialization
→ businessRuleAuthority = observable
```

and synthesize:

```text
Includes items from `_cards` only when `card.IsPublished`.
```

That Product Owner statement is false for the returned data.

This is not a benchmark-specific or malicious-syntax trick. Custom `IQueryProvider` implementations are a supported .NET extension point, and the runtime semantics of query execution are provider-defined.

## Required generic boundary

Exact resolution to `System.Linq.Queryable.<operation>` is not enough to prove product semantics.

A safe authority boundary must require something equivalent to:

```text
exact Queryable operation
+ source/provider identity proven
+ provider semantics for that operation proven/trusted
+ observable execution path proven
→ authoritative product rule

otherwise
→ observed-only / no authoritative Product Owner rule
```

A conservative V0.4.6 fix may simply downgrade `Queryable` business predicates unless provider semantics are deterministically proven.

If useful positive coverage must be retained for LINQ-to-Objects `AsQueryable()`, that safety must be proven from source/provider identity rather than from the `Queryable` method name alone.

Do not special-case PokeTrade, Loren, Jellyfin, EF, `Card`, or the exact regression source merely to preserve existing outputs.

## Required focused regression

Add a compile-valid custom `IQueryable<T>` / `IQueryProvider` fixture whose `CreateQuery` returns a query that retains the expression tree but enumeration ignores the `Where` predicate.

For:

```csharp
_cards.Where(card => card.IsPublished).ToList()
```

with an underlying unpublished card, generated knowledge must not contain an authoritative inclusion rule claiming returned items satisfy `card.IsPublished`.

A separate positive case may remain authoritative only when the provider semantics are actually proven by the implementation boundary.
