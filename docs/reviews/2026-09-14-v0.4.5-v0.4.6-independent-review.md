# V0.4.6 blockers

## B6.1 / P1 — syntax-only method-name matching can invent LINQ business semantics

Production code:

```text
src/Pkc.CSharp/CSharpBusinessPredicateEnricher.cs
```

`TryDescribe()` decides that an invocation is a business predicate only from:

```text
member method name ∈ { Where, Any, All, First, FirstOrDefault, Single, SingleOrDefault }
+ a supported expression lambda argument
```

It does not resolve the invoked symbol and does not prove the operation is `System.Linq.Enumerable` / `Queryable` or another explicitly supported semantic contract.

The business-predicate enricher runs **after** `CSharpProjectSemanticEnricher`, so these newly created `business-predicate` facts are not semantic-enriched afterwards. They also carry no `analysisMode` / `analysisConfidence` caveat of their own.

Therefore ordinary user code can produce a false high-level business rule.

Reachable example:

```csharp
public sealed class CustomBucket
{
    public IReadOnlyList<Card> Where(Func<Card, bool> ignored)
        => _allCards; // intentionally ignores the predicate
}

public IReadOnlyList<Card> GetCards()
    => _bucket.Where(card => card.IsPublished);
```

Current extraction can synthesize:

```text
Includes items from `_bucket` only when `card.IsPublished`.
```

That claim is false: the custom `Where` implementation does not filter by the lambda.

This violates the product contract that PO-facing business predicates must be deterministically grounded rather than inferred from lexical resemblance.

### Required fix

Regression-first. Add a negative custom-method regression that is red before the fix.

For a predicate to become authoritative business semantics, prove the invoked operation semantically, for example:

```text
resolved method belongs to supported System.Linq Enumerable/Queryable family
OR another explicitly defined semantic contract
```

If semantic resolution is unavailable, either omit the business-rule promotion or emit lower-confidence evidence that cannot become a definitive `Includes/Requires/Selects` rule.

Do not solve with method-name/repository/path exceptions.

## B6.2 / P1 — nested object creation is mislabeled as a configured item of the predicate source collection

Production code:

```text
src/Pkc.CSharp/CSharpBusinessPredicateEnricher.cs
```

`AddConfiguredSourceObjects()` takes the initializer of the predicate-source field and walks:

```text
initializer.DescendantNodesAndSelf()
→ every ObjectCreationExpression / ImplicitObjectCreationExpression
```

Every discovered object creation is emitted as:

```text
kind: configured-object
source: <predicate source member>
```

`GroundedKnowledgeSynthesizer` then renders each one as:

```text
Configured item in `<source>`: ...
```

This is only correct for object creations that are actually items of the source collection. Nested configuration objects are not collection items.

Reachable example:

```csharp
private readonly List<Card> _cards =
[
    new Card
    {
        Name = "A",
        Metadata = new CardMetadata
        {
            Name = "Internal metadata"
        }
    }
];
```

Current traversal can emit both the outer `Card` and nested `CardMetadata` as `configured-object` evidence for `_cards`, allowing knowledge to claim:

```text
Configured item in `_cards`: `Name = "Internal metadata"`.
```

That is a false product fact: the metadata object is not a card in `_cards`.

### Required fix

Regression-first with at least one nested object initializer.

Configured-item evidence must prove the object creation is a direct item/value of the supported source initializer shape, not merely a descendant object creation.

If collection element ownership cannot be proven, do not label the nested object as an item of the source collection. Preserve nested assignments only as part of their owning item when safely representable, or leave them unknown.

## B6.3 / P1 — Angular result/list flow cross-links different API services by method name alone

Production code:

```text
src/Pkc.Frontend/AngularListBehaviorScanner.cs
src/Pkc.Knowledge/CrossStackFeatureCandidateBuilder.cs
```

`AngularListBehaviorScanner` records a result binding with useful metadata including:

```text
service
apiMethod
target
component
```

However `CrossStackFeatureCandidateBuilder.AddResultFlowForApiCall()` and `FindScreensForResultFlow()` correlate that binding to a concrete `ui-api-call` by only:

```text
binding.apiMethod == apiCall.Container
```

`apiCall.Container` is the nearest method name containing the HTTP call. Service identity/source ownership is not part of the proof.

This creates a reachable false cross-stack observable-outcome claim whenever two API/service implementations use the same method name.

Example:

```text
CatalogApi.getCards()  → GET /api/cards
AdminApi.getCards()    → GET /api/admin/cards

CatalogComponent:
this.catalogApi.getCards().subscribe(cards => this.cards = cards)
@for (card of cards; ...)
```

When building the backend candidate for `/api/admin/cards`, current logic can find `AdminApi.getCards` as the matching `ui-api-call`, then attach the `CatalogComponent` binding/render simply because both methods are named `getCards`.

The generated knowledge can therefore claim that the admin endpoint feeds the public catalog list even though no such data flow exists.

The existing Mewtwo test passes because the controlled sample does not contain the ambiguous same-method-name shape.

### Required fix

Regression-first with two distinct Angular API/service implementations that intentionally share the same method name and route to different backend endpoints.

Result-flow proof must bind the component service reference to the same API/service implementation that owns the matched HTTP call. Acceptable deterministic evidence may include a grounded symbol/import/injection relation, class/member identity, or another conservative ownership key.

Method-name equality alone is insufficient. If service ownership cannot be proven, do not attach the result/list flow to the endpoint candidate.
