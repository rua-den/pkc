## B6.1 — BLOCK: line-range semantic proof can be borrowed by another invocation

### What improved

`CSharpBusinessPredicateEnricher` no longer trusts `Where`, `Any`, `All`, `First*` and `Single*` merely by lexical method name.

It requires an existing project-semantic `invokes` relation whose target is exactly:

```text
System.Linq.Enumerable.<operation>
System.Linq.Queryable.<operation>
```

That is the right authority direction.

### Remaining defect

The identity check for the invocation is not actually an exact syntax span. It compares only:

```text
owner fact
source path
StartLine
EndLine
```

`SourceLocation` contains only path/start-line/end-line, and `CSharpProjectSemanticEnricher` stores semantic invocation relations with that same line-level location.

Therefore two invocations on the same line inside the same callable are indistinguishable for this authority check.

### Reproducible counterexample

```csharp
public IReadOnlyList<Card> GetCards()
{
    _ = _bucket.Where(card => card.IsPublished); return _cards.Where(card => card.IsPublished).ToArray();
}
```

Assume:

```csharp
CustomBucket.Where(Func<Card, bool> ignored)
```

is a user-defined method that ignores the predicate, while `_cards.Where(...)` is the real LINQ operation.

The semantic relation set for that single source line can contain both:

```text
Demo.CustomBucket.Where
System.Linq.Enumerable.Where
```

When the business-predicate enricher processes the custom `_bucket.Where(...)`, its line-range lookup can find the LINQ relation belonging to the second invocation on the same line. The custom call is then incorrectly promoted to high-confidence `business-predicate` evidence.

This violates the accepted authority rule:

```text
No deterministic proof of this exact invocation → no authoritative business rule.
```

### Required regression

Add a real-project semantic regression containing a custom same-named operation and a genuine LINQ operation on the same source line. Assert that only the genuine LINQ invocation becomes authoritative business-predicate evidence.

### Required fix property

The semantic proof must identify the exact invocation, not merely its line range. Acceptable directions include:

- carry exact syntax span/column provenance into semantic invocation evidence; or
- resolve the invocation symbol directly from the same semantic model when constructing the business-predicate evidence.

Do not solve only `Where`; the proof must remain generic for the supported operation table.

## B6.3 — BLOCK: simple class names are not unique Angular service identities

### What improved

Result/list correlation now requires both:

```text
binding.apiMethod == apiCall.Container
binding.serviceType == apiCall.ownerClass
```

The focused `CatalogApi` versus `AdminApi` test closes the original method-name-only collision.

### Remaining defect

Both `serviceType` and `ownerClass` are simple TypeScript class names. The correlation does not prove module/import identity.

Different modules can validly export classes with the same simple name.

### Reproducible counterexample

```text
catalog/cards-api.ts
  export class CardsApi {
    getCards() → GET /api/cards
  }

admin/cards-api.ts
  export class CardsApi {
    getCards() → GET /api/admin/cards
  }

catalog.component.ts
  import { CardsApi } from './catalog/cards-api'
  private readonly api = inject(CardsApi)
  api.getCards() → this.cards
  @for (card of cards; ...)
```

The current evidence can become:

```text
binding.apiMethod  = getCards
binding.serviceType = CardsApi

catalog API ownerClass = CardsApi
admin API ownerClass   = CardsApi
```

For the admin endpoint, route matching selects the admin `ui-api-call`, then the service-aware correlation still accepts the Catalog component binding because the simple type names are equal.

The admin endpoint can therefore inherit a rendered Catalog list that it does not feed.

### Required regression

Use two different TypeScript modules exporting the same class name and method name with different endpoint routes. Only the actually imported/injected module must be allowed to feed the component list.

### Required fix property

Use a deterministic service identity strong enough to distinguish same-named classes from different modules, for example import/module-qualified identity when syntax can prove it.

If module ownership cannot be proven, omit the endpoint-to-list claim rather than correlating by simple class name.

## B6.4 — BLOCK: operation semantics do not prove observable business effect

This is a new blocker found while challenging the V0.4.6 product contract. It is not a request for arbitrary-program reconstruction.

### Current behavior

Once a supported LINQ invocation is recognized, `CSharpBusinessPredicateEnricher` attaches the resulting `business-predicate` to its callable using `contains-condition`.

`FeatureCandidateBuilder` treats `contains-condition` as behavior evidence and carries it into endpoint candidates reached through the callable graph.

`GroundedKnowledgeSynthesizer` then promotes the operation into product wording such as:

```text
Includes items from `_cards` only when `...`.
Requires at least one item from `_cards` to satisfy `...`.
Selects an item from `_cards` where `...`.
```

The compiler currently proves that the operation exists, but does not prove that its result controls the endpoint return, eligibility decision, guard, mutation or another observable outcome.

### Reproducible false-product claim

```csharp
public IReadOnlyList<Card> GetCards()
{
    var published = _cards.Where(card => card.IsPublished).ToArray();
    Audit(published.Length);
    return _cards;
}
```

`_cards.Where(...)` really is `System.Linq.Enumerable.Where`, so B6.1 semantic operation proof legitimately succeeds.

But the endpoint returns the unfiltered `_cards` collection.

Current synthesis can still tell the Product Owner:

```text
Includes items from `_cards` only when `card.IsPublished`.
```

That statement is false for the observable result.

The same problem affects operation-context polarity. For example:

```csharp
if (_cards.Any(card => card.Blocked))
{
    throw new InvalidOperationException();
}
```

The raw fact that `Any(card => card.Blocked)` occurs is true, but generic wording such as `Requires at least one item ... to satisfy ...` does not represent the actual business rule, which rejects when any blocked item exists.

### Required regression

At minimum add a real C# regression proving that a supported LINQ predicate whose result does not determine the endpoint return/decision is not rendered as an authoritative endpoint inclusion rule.

Also protect operation context/polarity for `Any`/`All`/selection operations before using requirement-style wording.

### Required fix property

Separate:

```text
observed local query predicate
```

from:

```text
proven observable business rule
```

Promote to authoritative Product Owner wording only when deterministic control/data-flow evidence proves the predicate participates in the observable outcome. Otherwise keep the evidence local/lower-authority or omit the product-level rule.

The V0.4.6 milestone does not need arbitrary-program data-flow completeness, but it must not convert an observed LINQ call into a stronger endpoint behavior claim than the compiler can prove.
