## Counterexample

A normal Angular inline template can contain:

```html
<section [hidden]="true">
  @if (displayPrice > 0) {
    <strong>{{ displayPrice }}</strong>
  }
</section>
```

This is compile-valid and runtime-valid. Angular sets the native element `hidden` property to true. The subtree is therefore not presented to the user even when the `@if` condition is true.

## Violated proof boundary

## Required regression-first repair

The minimum generic repair is to close the native HTML `hidden` binding family at the render-authority boundary without expanding into a general browser/CSS solver.

Required semantics:

```text
[hidden]="true"                       → reject render authority
bind-hidden="true"                    → reject render authority
[hidden]="expression"                 → fail closed
[hidden]="False"                      → fail closed; Angular expression identifiers are case-sensitive
hidden="{{ expression }}"             → fail closed
[attr.hidden]="expression"            → fail closed
bind-attr.hidden="expression"         → fail closed
[hidden]="false" / bind-hidden="false" → positive safeguard
```

The exact lowercase literal `false` property binding is the only supported bound-hidden positive because it deterministically disables the native hidden property. Attribute-binding forms are not equivalent: presence of the boolean HTML attribute can still suppress presentation.

Do not opportunistically expand this repair into class/stylesheet CSS, computed CSS, signals, outlets, arbitrary DOM property evaluation, or general runtime layout semantics.
