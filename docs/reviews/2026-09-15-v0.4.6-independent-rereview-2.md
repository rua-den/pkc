
5. accepts only exact supported targets:


The focused regression `Same_line_custom_Where_cannot_borrow_real_Linq_Where_semantic_authority` exercises the original same-line collision and asserts only the genuine LINQ invocation survives.

## B6.3 — BLOCK: commented import-like text can override the real Angular service identity

### What improved

Production code now represents API service ownership as:

```text
<normalized source module path>#<exported class>
```

and cross-stack result/list correlation requires exact identity equality. That closes the previous ordinary same-class-name/different-module fixture.

### Remaining authority defect

`AngularServiceIdentityEnricher.GetImportsAsync` does not obtain imports from the TypeScript AST. It scans the entire raw source text using `NamedImportRegex`:

```text
import\s*\{ ... \}\s*from\s*['\"]...['\"]
```

This scan is not comment- or string-aware. Every textual match updates the same local-name dictionary:

```text
result[localName] = imported type
```

so a later commented import-like line can overwrite the real active import and become authoritative ownership evidence.

### Reproducible counterexample

Files:

```text
catalog/cards-api.ts
  export class CardsApi {
    getCards() -> GET /api/cards
  }

admin/cards-api.ts
  export class CardsApi {
    getCards() -> GET /api/admin/cards
  }
```

Valid component source:

```ts
import { Component, inject } from '@angular/core';
import { CardsApi } from './catalog/cards-api';

// Historical note only; this is NOT an import:
// import { CardsApi } from './admin/cards-api';

@Component({
  selector: 'app-catalog',
  template: `
    @for (card of cards; track card.id) {
      <article>{{ card.name }}</article>
    }
  `
})
export class CatalogComponent {
  private readonly api = inject(CardsApi);
  cards = [];

  reload() {
    this.api.getCards().subscribe(cards => this.cards = cards);
  }
}
```

TypeScript uses the active Catalog import. The comment has no semantic effect.

Current PKC raw-text import resolution can nevertheless match the commented line after the real import, overwrite `CardsApi` ownership with:

```text
admin/cards-api.ts#CardsApi
```

and then `CrossStackFeatureCandidateBuilder` can match the Catalog component result/list binding to the admin API call because the rewritten `serviceType` equals the admin `ownerClass`.

Observable false claim:

```text
/api/admin/cards
→ CatalogComponent.cards
→ catalog rendered list
```

although the component actually imports and calls the Catalog service.

This is blocker-class because inactive trivia is being used as deterministic cross-layer ownership authority.

### Required fix property

Do not implement in the review thread. The coding pass must establish this property generically:

```text
only syntactically active import declarations may establish service ownership
comment/string/template import-like text must have zero authority
ambiguous or unresolved ownership must omit the endpoint-to-result/list correlation
```

AST-backed import extraction is one acceptable direction; any alternative must provide equivalent syntax-aware authority.

Add an adversarial regression with a real import plus a later commented import-like collision before fixing.

## B6.4 — BLOCK: return containment does not prove value semantics or polarity

### What improved

The current filter correctly downgrades supported LINQ predicates that are not in a return/yield-return syntax path to observed-only evidence. This closes the original local-discarded-query fixture and prevents a throwing `Any` guard from being rendered as a positive existence requirement.

Direct positive `Any` and `All` returns also no longer use `Requires ...` wording.

### Remaining authority defect

`GetObservableContext` marks an invocation observable when it appears anywhere inside the returned expression:

```text
return-expression contains invocation
arrow-expression contains invocation
yield-return expression contains invocation
```

That proves syntactic containment only. It does not prove that enclosing operators/calls preserve the invocation's value, polarity, or result type.

Once marked `observable`, the relation remains `contains-condition`, and synthesis emits operation-specific Product Owner wording without inspecting the enclosing expression.

### Counterexample A — boolean polarity inversion

Valid C#:

```csharp
public bool HasNoBlockedCards()
    => !_cards.Any(card => card.Blocked);
```

The exact `Any(...)` invocation is genuine LINQ and is contained in the arrow return, so current authority marks it observable.

Current synthesis can emit:

```text
Returns whether at least one item from `_cards` satisfies `card.Blocked`.
```

Actual behavior is the opposite:

```text
returns true only when no blocked card exists
```

The same class of error applies to negated `All(...)`.

### Counterexample B — selection transformed into a boolean

Valid C#:

```csharp
public bool HasNoPublishedCard()
    => _cards.FirstOrDefault(card => card.IsPublished) is null;
```

`FirstOrDefault(...)` is contained in the returned expression, so current code treats the selection predicate as observable and synthesis can say:

```text
Returns an item from `_cards` selected where `card.IsPublished`.
```

The method actually returns a boolean indicating that no matching item was selected.

This directly violates the requested `First*` / `Single*` context requirement.

### Counterexample C — returned syntax contains a predicate that an outer helper discards

Valid shape:

```csharp
public IReadOnlyList<Card> GetCards()
    => ReturnAll(_cards.Where(card => card.IsPublished).ToArray());

private IReadOnlyList<Card> ReturnAll(IReadOnlyList<Card> ignored)
    => _cards;
```

The genuine `Where(...)` is syntactically inside the return expression, so the current filter promotes it. Synthesis can claim:

```text
Includes items from `_cards` only when `card.IsPublished`.
```

but the helper discards the filtered argument and returns all cards.

This is the original B6.4 authority principle at one additional expression boundary: observable syntax containment is not equivalent to proven observable effect.

### Required fix property

Do not implement in the review thread. The coding pass must establish a conservative semantic boundary:

```text
predicate invocation
+ proven value/polarity-preserving path to observable result
→ authoritative Product Owner rule

otherwise
→ observed-only / lower authority / omit product-level claim
```

At minimum, regressions must challenge:

```text
!Any(...)
!All(...)
FirstOrDefault(...) is null
SingleOrDefault(...) is not null
predicate passed through an arbitrary helper that does not preserve the value
positive direct Any/All returns
positive returned Where/selecting pipelines
throwing/rejecting guards
```

If an enclosing transformation is not modeled deterministically, omission/lower authority is preferable to a stronger claim.
