## B1 — still blocking: canonical operand normalization is lossy

The fix correctly replaced existential single-key matching with complete requiredness-condition-set comparison and rejects unsupported boolean forms conservatively. Compound `&&`, reversed equality operands, conditional/unconditional mismatch, and multiple requiredness facts are regression-covered.

However, `ValidationConsistencyCandidateEnricher.CanonicalOperand()` still sends operands through `NormalizeToken()`, which removes every non-alphanumeric character and lowercases the result. The equality parser explicitly accepts signed/decimal numeric literals and quoted strings, so this normalization can collapse semantically different conditions before the set comparison.

Concrete reachable counterexamples:

```text
UI:      retryCount === -1
Backend: request.RetryCount == 1

canonicalized by current code:
retrycount=1
retrycount=1
→ false `consistent` / high confidence
```

```text
UI:      threshold === 1.2
Backend: request.Threshold == 12

current normalization:
1.2 → 12
12  → 12
→ false equivalence
```

```text
UI:      code === 'A-B'
Backend: request.Code == "AB"

current normalization:
'A-B' → ab
"AB"  → ab
→ false equivalence
```

The same helper also reduces member access to its terminal segment. Distinct paths ending in the same member name can therefore collapse, for example `primary.status` versus `secondary.status`, unless some other evidence prevents the comparison.

This violates the original B1 acceptance requirement:

> Preserve the full condition semantics that PKC can prove. If equivalence cannot be proven deterministically, do not emit `consistent`.

### Required B1 follow-up

Regression-first, add tests that prove at minimum:

```text
- signed numeric values remain distinct: -1 != 1
- decimal structure remains distinct: 1.2 != 12
- quoted punctuation remains significant: "A-B" != "AB"
- distinct member paths are not collapsed merely because the terminal name matches
```

Then change condition canonicalization so it preserves meaning rather than stripping punctuation/path structure. Cross-language conveniences such as `serviceType === 'CSP'` matching `request.ServiceType == ServiceType.CSP` must only be retained where the equivalence rule is explicit and deterministic.

If PKC cannot prove a cross-language equivalence, classify conservatively as `possible-mismatch`/`unknown`, never `consistent/high`.
