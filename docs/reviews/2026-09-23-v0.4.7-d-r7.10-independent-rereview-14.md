## Counterexample — external attribute/class component selector

An installed Angular dependency can export a component whose selector uses a native element plus an attribute:

```ts
@Component({
  selector: 'div[ext-shell]',
  template: `<span>Shell</span>`
})
export class ExternalShell {}
```

Product code can import that component and use:

```ts
@Component({
  imports: [ExternalShell],
  template: `
    @if (isAllowed) {
      <div ext-shell>{{ displayPrice }}</div>
    }
  `
})
export class PriceComponent {}
```

Angular supports element, attribute, class and combined component selectors. Child content under a component host is rendered only through a matching `ng-content` projection slot. The external component above has no slot, so `displayPrice` is not inserted into rendered DOM.

On `3e6fa774...`, `AngularComponentProjectionAuthorityFilter` inventoried selectors only from product-source `@Component` decorators. `FrontendSourceScope` excludes `node_modules`, so the external attribute/class selector was unknown. The native-looking host could therefore retain authoritative `ui-member-render`, acquire the enclosing supported `@if`, and feed false R7.9/R7.10 rendered-value and joint-visibility authority.

## Violated proof boundary

The accepted boundary requires an authoritative active directly-rendered Angular text interpolation. Lexical child content of a component host is not direct rendered output when the receiving component does not project it.

This is not a request for a general Angular compiler or projection-slot solver. It is a concrete selector-identity gap at the existing fail-closed projection boundary.
