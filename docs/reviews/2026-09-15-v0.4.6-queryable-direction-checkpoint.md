## Why this is the right boundary

Resolving a call to `System.Linq.Queryable` identifies an expression-building/provider-mediated API, not proof that an arbitrary runtime provider applies the predicate. A provider can retain the expression tree while enumerating the original unfiltered items.

The implementation deliberately trades coverage for soundness:

1. `CSharpBusinessPredicateAuthorityFilter.GetObservableContext` returns no observable authority for every exact Queryable predicate target.
2. `IsAllowedWherePipelineInvocation` rejects every `System.Linq.Queryable.*` hop before the old preservation allowlists. This also prevents an Enumerable `Where` from inheriting authority through a later unproven Queryable operation.
3. Predicates remain facts, with `businessRuleAuthority=observed-only` and an `observes-predicate` relation.
4. `FeatureCandidateBuilder` retains that relation/fact so downgrading authority does not erase evidence.

This is generic: there are no benchmark names, entity names, provider brands, or expression-text exceptions. Pure Enumerable preservation remains covered. Even ordinary LINQ-to-Objects `AsQueryable()` chains lose authority under this conservative version; no provider-identity proof has been implemented. Do not undo that downgrade just to recover a benchmark sentence.

## Regression quality and remaining gaps

Committed regressions check:

- Directly returned custom-provider `Where(...).ToList()` is observed-only, lacks observable context, omits the false inclusion rule, and retains predicate evidence.
- Enumerable filtering followed by a Queryable hop is downgraded and retains evidence.
- A pure Enumerable pipeline still produces the inclusion rule.
- An in-process executable custom provider returns an unpublished item despite `Where(card => card.IsPublished)`.

Earlier WIP mistakes were corrected before the implementation commit: invalid instance-field initialization, a negative assertion naming the wrong source, a local-variable return shape that already downgraded in the old implementation, and a Windows-specific MSBuild registration workaround.

Nonblocking gaps to carry forward:

1. The new tests stop at `FeatureKnowledge.Rules` / `Evidence`; they do not directly assert workflow/product Markdown or folder/bundle/ZIP parity for this fixture. Current rendering was inspected in source.
2. `KnowledgeEvidence` does not carry the explicit `businessRuleAuthority` metadata. Its description is `Business predicate: ...`; lower authority is conveyed by placement in Evidence. An explicit observation label could improve interpretation, but requires a deliberate follow-up and portable-output tests.
3. The analyzed source fixture and in-process runtime fixture are separate definitions. A one-time standalone build confirmed the analyzed shape compiles, but future divergence is not automatically prevented. Prefer compiling/executing the same fixture if extending these tests.
4. Queryable entries remain in old preservation allowlists behind the unconditional rejection guard. They are unreachable today; future refactoring must preserve the guard or introduce actual provider proof.
5. Direct Queryable operations other than Where are covered by the generic production guard, not by a new per-operation regression matrix in this commit.

Do not classify these gaps as acceptance or as new blockers without a concrete failing behavior. Do not broaden into V0.4.7 while the review-9 acceptance sequence remains open.
