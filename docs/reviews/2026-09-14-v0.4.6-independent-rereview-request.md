## B6.1 — supported LINQ/business-predicate operation authority

### Red regression

```text
commit: f09658a8f5f097abd4003b15e5261a5388691488
run:    34806787160
```

Adversarial fixture defines a custom method named `Where` whose lambda is ignored:

```csharp
public IReadOnlyList<Card> Where(Func<Card, bool> ignored) => _allCards;
```

Before the fix, PKC incorrectly emitted an authoritative `business-predicate` for that call.

Expected red result was observed:

```text
C# tests: 1 failed / 57 passed / 58 total
failing regression: Custom_method_named_Where_does_not_become_authoritative_business_predicate
```

### Generic fix

```text
commit: b13b9d7b0a89f2df0100fa5f8e22a7969b0fdf30
positive-proof hardening: 0bc0be87e94472d6a972899a3928085ba3ef636d
```

`CSharpBusinessPredicateEnricher` now requires a project-semantic invocation relation at the same invocation source span. Only exact supported targets are authoritative:

```text
System.Linq.Enumerable.<supported operation>
System.Linq.Queryable.<supported operation>
```

The rule applies through the shared operation table for `Where`, `Any`, `All`, `First*` and `Single*`; method-name equality alone is no longer sufficient.

Positive predicate evidence now carries:

```text
operationResolution = project-semantic
operationSymbol     = System.Linq.Enumerable.Where / System.Linq.Queryable.Where / ...
analysisConfidence  = high
```

Unresolved or custom operations are conservatively omitted from authoritative business-predicate knowledge.

## B6.3 — Angular service-aware result/list correlation

### Red regression

```text
commit: aee74969d26627ba7e446de3e28bed5ce6276110
run:    34807296605
```

Adversarial fixture:

```text
CatalogApi.getCards() → GET /api/cards
AdminApi.getCards()   → GET /api/admin/cards

CatalogComponent injects only CatalogApi
CatalogComponent.reload()
  → catalogApi.getCards()
  → this.cards
  → @for card of cards
```

Before the fix, `/api/admin/cards` inherited the Catalog component binding/list flow solely because both API service methods were named `getCards`.

Expected red result was observed:

```text
frontend tests: 1 failed / 10 passed / 11 total
C# tests:       59 / 59 PASS
```

### Generic fix

```text
b63d79ba51ab08b82e3e1a468e96974289660d8e  capture binding service type
5264f1c6ba8011c901e00360a612be3a0aecc68d  capture fallback API owner class
06af278dc4cf51dd3152eaf8693b17e2fa6853d6  capture AST API owner class
478e92343154083c3987f07e4fbad66a042c25e8  require service-owner equality
```

Angular result bindings syntactically resolve the service variable to a service type from supported forms such as `inject(ServiceType)`, constructor DI and direct `new ServiceType(...)`.

Angular API-call evidence now carries the containing API service class where syntactically provable.

Authoritative result/list correlation requires:

```text
binding.apiMethod == apiCall.Container
AND binding.serviceType == apiCall.ownerClass
```

If service ownership cannot be proved, PKC conservatively omits the endpoint-to-list claim.
