## B6.1 — exact semantic invocation identity

### Original blocker

Two same-line invocations inside the same callable could be indistinguishable by line-range correlation, allowing a custom `Where` to borrow semantic authority from a genuine LINQ `Where`.

Adversarial shape:

```csharp
_ = _bucket.Where(card => card.IsPublished); return _cards.Where(card => card.IsPublished).ToArray();
```

where `_bucket.Where(...)` is user-defined and ignores the predicate.

### Focused regression

```text
Same_line_custom_Where_cannot_borrow_real_Linq_Where_semantic_authority
```

Regression-first evidence:

```text
RED commit   cf7645eef7b22d82803ea9f48e7575677b8d2a07
RED run      34813594610 — FAIL expected
FIX commit   d784013b54acbec22dc9c18a3cfa738b38adc3d3
GREEN run    34813887033 — PASS
```

### Current implementation property to verify

`CSharpBusinessPredicateAuthorityFilter` uses the predicate invocation span start to locate the exact `InvocationExpressionSyntax` in the real project syntax tree and re-resolves that exact invocation through Roslyn semantic model.

Authoritative predicate evidence survives only when the exact resolved target is:

```text
System.Linq.Enumerable.<operation>
System.Linq.Queryable.<operation>
```

If the exact invocation cannot be resolved uniquely/proven, the authoritative predicate is rejected.

### Reviewer challenge

Try to break exact identity with:

- same-line custom + LINQ invocations;
- supported operation names beyond `Where` (`Any`, `All`, `First*`, `Single*`);
- overloaded/candidate-symbol ambiguity;
- multi-project source collisions where exact project ownership is not uniquely provable.

PASS B6.1 only if no custom invocation can acquire LINQ authority from another syntax node.

## B6.3 — deterministic Angular service identity

### Original blocker

Different TypeScript modules can export the same class and method names:

```text
catalog/cards-api.ts → export class CardsApi { getCards() → /api/cards }
admin/cards-api.ts   → export class CardsApi { getCards() → /api/admin/cards }
```

A Catalog component importing only `./catalog/cards-api` must never feed the admin endpoint merely because both owners are named `CardsApi`.

### Focused regression

```text
Same_service_class_name_in_different_modules_does_not_cross_link_list_flow
```

Regression-first evidence:

```text
RED commit   df1ea834b970201b511c8ff9a975f4e1fe59c53d
RED run      34814066361 — FAIL expected
FIX commit   84da527e8341918b1803e36ccd177a4d14056cd8
GREEN run    34814396514 — PASS
```

### Current implementation property to verify

`AngularServiceIdentityEnricher` assigns API owners a deterministic identity using:

```text
normalized source module path + exported owner class
```

For result bindings it parses named imports, resolves supported relative module paths against actual product-source `.ts` files, normalizes aliases to the exported class, then uses:

```text
resolved module path + exported class
```

`CrossStackFeatureCandidateBuilder` requires exact equality between binding service identity and API owner identity before adding authoritative result/list flow.

If deterministic module identity cannot be proven, the simple class name is not sufficient to correlate.

### Reviewer challenge

Try:

- same class + same method in different modules;
- named import aliases;
- nested relative paths and `../` normalization;
- supported `index.ts` resolution;
- unresolved/non-relative imports;
- ambiguous module shapes.

PASS B6.3 only if absence of deterministic module identity removes the authoritative cross-stack match rather than falling back to simple-name certainty.

## B6.4 — observable predicate authority and operation polarity

### Original blocker

A genuine supported LINQ call was previously enough to create Product Owner rule wording even when the predicate result did not determine the endpoint's observable outcome.

Canonical false-product-claim shape:

```csharp
public IReadOnlyList<Card> GetCards()
{
    var published = _cards.Where(card => card.IsPublished).ToArray();
    Audit(published.Length);
    return _cards;
}
```

The compiler must not tell a PO:

```text
Includes items from `_cards` only when `card.IsPublished`.
```

because the endpoint returns unfiltered `_cards`.

The previous review also challenged operation polarity:

```csharp
if (_cards.Any(card => card.Blocked))
    throw new InvalidOperationException();
```

must not become a positive requirement that a blocked item exists.

### Focused regressions

```text
Local_query_predicate_that_does_not_affect_return_is_not_an_authoritative_rule
Any_guard_that_throws_is_not_rendered_as_a_positive_existence_requirement
Returned_filter_predicate_remains_authoritative
Direct_any_return_is_observable_but_not_rendered_as_a_requirement
Direct_all_return_is_observable_but_not_rendered_as_a_requirement
```

Regression/fix history:

```text
observable-authority RED run     34817523642 — expected B6.4 failures
observable filter fix commit     304a39053b243bceb6c39d85f47cc7fab68fd57f
polarity RED commit              39079f0b7a8f9abccc850f3464202f57f9caa220
polarity RED run                 34817972557 — 2 expected failures
final B6.4 fix commit             34c3bf00233ac4c0c4df717f7f7c5ae55fffe07b
```

### Current implementation property to verify

Valid supported LINQ predicates are retained as evidence, but authority is separated:

```text
no proven direct observable return/yield participation:
  businessRuleAuthority      = observed-only
  observableEffectResolution = not-proven
  relation                   = observes-predicate

proven direct return/yield participation:
  businessRuleAuthority      = observable
  observableContext          = return | yield-return
  observableEffectResolution = direct-return-syntax
  relation remains           = contains-condition
```

`GroundedKnowledgeSynthesizer` only turns `contains-condition` business predicates into product-level rules.

Reviewed operation-context wording is now intended to be:

```text
Where feeding returned collection:
  Includes items ... only when ...

Any direct return:
  Returns whether at least one item ... satisfies ...

All direct return:
  Returns whether every item ... satisfies ...

selection direct return:
  Returns an item ... selected where ...
```

Non-observable Any/All predicates must not be rendered as positive requirements. A rejecting `if (...) throw` may still be represented through the ordinary condition + throw evidence, preserving rejection polarity without promoting the nested LINQ fact itself.

### Reviewer challenge

Do not stop at the committed fixtures. Construct adversarial variants involving:

- local side-path predicates whose result is logged/audited but not returned;
- nested lambdas/local functions inside a method;
- Any/All used in rejecting guards;
- direct Any/All boolean returns;
- direct `First*`/`Single*` selection returns;
- returned `Where` pipelines;
- syntax where an observed LINQ invocation is reachable but does not determine the endpoint result.

The accepted V0.4.6 scope does not require arbitrary whole-program data-flow completeness. It **does** require conservative authority: when observable participation cannot be deterministically proved, keep/lower evidence rather than produce a stronger endpoint product claim.

PASS B6.4 only if no blocker-class false-product-claim path remains within that supported authority model.
