## Rereview-7 blocker disposition

Rereview 7 showed that a same-type method-group projection could preserve an earlier authoritative `Where` predicate while a copy constructor mutated the filtered source item before initializer values were copied.

Production `868195eff...` closes that gap inside the same preservation proof. `IsPredicatePreservingSameTypeMethodGroupProjection()` now requires `IsEffectSafeObjectConstruction()` before it accepts the existing direct-copy initializer proof.

The construction proof is conservative and generic:

```text
zero object-construction arguments
+ resolved symbol is a constructor
+ constructor is compiler-generated / implicitly declared
+ constructor has zero parameters
+ constructor belongs exactly to the projected type
+ class directly derives from System.Object
+ no instance field initializer
+ no instance event-field initializer
+ no instance property initializer
+ existing same-type / direct stored-member / direct same-member copy proof
+ complete predicate-member coverage
→ earlier Where semantics may remain authoritative

otherwise
→ fail closed / observed-only
```

This is sufficient for the rereview-7 defect: source-mutating copy constructors, explicit user code in a parameterless constructor, instance initialization code, and effectful non-`object` base-constructor paths cannot satisfy the preservation proof.

## Adversarial review

The implementation was challenged beyond the four added regressions.

### Constructor overloads and zero-argument syntax

A constructor call with arguments fails immediately on syntax argument count.

A user-defined constructor callable with zero supplied arguments through optional parameters or `params` still fails because the resolved constructor is not implicitly declared and its semantic parameter count is not zero.

An explicit user-defined parameterless constructor also fails because `IsImplicitlyDeclared` is false.

No overload-resolution route was found that can produce a compile-valid call while resolving to a different effectful constructor and still satisfy all of the exact constructor-symbol checks.

### Target-typed `new`, explicit `new Type()` and parentheses

Target-typed `new()` and explicit `new Type()` both resolve through the same semantic constructor check. Parenthesized object creation is explicitly unwrapped.

Other expression wrappers are not broadened into trusted construction shapes; they fail closed because the accepted construction syntax is limited to object creation or implicit object creation.

### Partial types and instance initialization

`HasInstanceInitializationCode()` walks every `DeclaringSyntaxReference` for the projected named type. Therefore an instance field, event-field or property initializer in another partial declaration still downgrades authority.

The check is intentionally conservative: harmless instance initialization can also cause downgrade. That is acceptable because false-negative authority is safer than a false Product Owner rule.

### Inheritance and base constructors

For classes, the projected type must directly derive from `System.Object`. A derived type with any custom/non-`object` base path is rejected before initializer safety is considered.

Structs do not execute a user-defined base-class constructor path, while any user-defined parameterless struct constructor still fails the implicit-constructor requirement.

### Semantic-resolution edge cases

The code requires the selected constructor symbol to be an `IMethodSymbol` of `MethodKind.Constructor`, implicitly declared, zero-parameter, and owned by the exact projected type.

Candidate-symbol fallback does not provide a compile-valid bypass: an ambiguous or otherwise unresolved construction cannot satisfy normal compile-valid overload resolution, while a single candidate still has to satisfy the same exact constructor constraints.

### Existing positive and closed paths

The positive safe defensive-clone regression remains valid: sealed same-type item, implicit inert construction, no instance initializer, direct auto/stored member copies, and complete predicate-member coverage.

Direct identity `Select(card => card)` remains on its separate identity-projection proof and is unaffected by the constructor restriction.

The rereview-6 callback/comparer pipeline boundary is unchanged by this checkpoint. `OrderBy*`, `ThenBy*`, `Distinct`, and `ToHashSet` are not reintroduced as unconditional preserving operations. No concrete contradiction was found, so that blocker remains closed.

B6.1, B6.2 and B6.3 were not reopened; the reviewed production commit changes only the generic business-predicate authority filter and its constructor-authority regressions.
