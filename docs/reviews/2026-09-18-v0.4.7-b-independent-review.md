## P1 — unsupported simple writes can leave stale terminal authority

The B analyzer tracked supported assignments only when the whole statement was a direct assignment expression. Its preflight rejected compound and unary writes, but skipped simple assignments nested inside another statement or contained in a complex top-level left-hand side.

Two compile-valid executable counterexamples demonstrated the same root cause:

```csharp
service.NetPrice = service.Price - service.Discount; // stored derivation: 90
var observed = (service.NetPrice = 5m);              // nested simple write
return service.NetPrice;                             // runtime: 5
```

and:

```csharp
service.NetPrice = service.Price - service.Discount; // stored derivation: 90
decimal observed;
(service.NetPrice, observed) = (5m, 0m);             // deconstruction write
return service.NetPrice;                             // runtime: 5
```

Before repair, both fixtures compiled and returned `5`, while PKC emitted `value-terminal-source` pointing to the earlier derivation. The derivation fact itself remains correct historical evidence; only the claim that it is the last source before return is false.

## Repair boundary

For each statement, inspect simple assignments which are not a directly supported property assignment. Resolve property write targets from their left-hand side and invalidate only the matching current-value slots. This covers nested assignments and complex/deconstruction targets without deleting earlier derivation evidence or adding a general expression solver.

Permanent regressions require all three conditions:

1. exact fixture compilation and runtime result `5`;
2. the earlier `service.Price - service.Discount → service.NetPrice` derivation remains retained;
3. no authoritative terminal-source fact is emitted after the unsupported write.

### Verdict: FAIL V0.4.7-B

A new compile-valid/runtime-valid stale-terminal-source counterexample remains through **deconstruction reference reassignment**.

Focused fixture shape:

```csharp
var service = new Service();
var alias = new Service();
var other = new Service();

service.Price = 100m;
service.Discount = 10m;
service.NetPrice = service.Price - service.Discount; // proven derivation: 90

(alias, other) = (service, alias);                    // alias now references service
alias.NetPrice = 5m;                                 // runtime write reaches service.NetPrice
return service.NetPrice;                             // runtime result: 5
```

This uses only straight-line code, fresh object allocations, ordinary reference assignment through tuple deconstruction, auto scalar properties, and no invocation/branch/custom accessor/conversion/operator effect.

Expected safe behavior:

```text
derivation fact remains as historical evidence
no value-terminal-source fact may claim that derivation is still current at return
```

Current analyzer behavior remains vulnerable because the two fail-closed mechanisms do not meet at this shape:

1. `HasReferenceAmbiguity` tests `GetSymbolInfo(assignment.Left).Symbol` as one local/parameter symbol. A deconstruction left side is a tuple expression rather than one reassigned local, so the alias reassignment is not rejected by that check.
2. The repaired per-statement invalidation walks `MemberAccessExpressionSyntax` nodes in the assignment left side. `(alias, other)` contains local identifiers, not member-access write targets, so it does not invalidate the previously proven `service.NetPrice` slot.
3. The later supported write `alias.NetPrice = 5m` updates/removes only the slot keyed by receiver identity `alias`; the earlier `service.NetPrice` slot remains keyed by receiver identity `service`.
4. `return service.NetPrice` can therefore still resolve the stale derivation and emit `value-terminal-source`, even though both variables now reference the same runtime object and the returned value is `5`.

This is the same product-level defect class as the repaired blocker: historical derivation evidence is valid, but terminal-source authority can become stale after an unsupported write/alias effect.
