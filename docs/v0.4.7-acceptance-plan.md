## Product-knowledge invariants

Keep business conditions, value lineage/provenance, mutation/causality, and presentation authority distinct. Deterministically proven observable behavior may become authoritative product-behavior knowledge. Unsupported inference fails closed. Same/similar names are never sufficient proof.

## Product Owner acceptance questions

Generated portable knowledge must answer these questions from evidence or explicitly say the answer is not proven:

1. Where did this value originally come from?
2. If the upstream value changes later, does the existing downstream value change automatically?
3. What code path can change this value after creation?
4. Was this value directly copied or computed?
5. What was the last observed source before a supported persistence/return boundary?
6. What backend conditions and frontend conditions jointly determine whether an item/value is visible?
7. How does a value travel through backend → DTO/projection → API → frontend composition?
8. If authority is incomplete, what lineage or causal evidence is still deterministically known?

Raw fact existence alone is insufficient; portable knowledge must support a PO-level answer.

#### Rereview #7 finding

After six earlier render/presentation false-positive classes had been repaired, independent rereview #7 found a distinct control-flow scope bug on exact `5d43b180...`:

```html
@if (isAllowed) {
  <!-- { -->
}
<strong>{{ displayPrice }}</strong>
<!-- } -->
```

Angular treats the braces inside HTML comments as inert. The interpolation is therefore outside the real `@if`. The previous brace matcher counted those commented braces and could incorrectly emit `ui-member-visibility(isAllowed)`, allowing a false R7.10 joint-visibility rule despite a valid R7.9 render fact.

Review record:

`docs/reviews/2026-09-22-v0.4.7-d-r7.10-independent-rereview-7.md`


The bounded `@if` scope matcher now skips complete HTML-comment regions while counting braces and fails closed on an unterminated comment. Regression coverage:
