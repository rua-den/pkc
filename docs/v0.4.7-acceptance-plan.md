## Product-knowledge invariants

V0.4.7 extends the compiler without collapsing the permanent knowledge classes:

```text
business conditions
value lineage / provenance
mutation / causality
```

They may be connected in a PO-facing explanation, but one must not be silently promoted into another.

Authority rule:

```text
deterministically proven observable behavior
→ may become an authoritative product-behavior claim

deterministic implementation evidence without full authority
→ retain as lower-authority lineage / provenance / mutation / causal evidence

unsupported inference
→ do not invent
```

Conservative authority downgrade must never erase deterministic lower-authority evidence.

## V0.4.7 Product Owner acceptance questions

Generated portable knowledge must answer these questions from evidence, or explicitly say the answer is not proven:

1. **Where did this value originally come from?**
   - Identify the earliest deterministically proven source in the observed lineage.
   - Show intermediate entity/property edges; never jump by name similarity.

2. **If the upstream value changes later, does the existing downstream value change automatically?**
   - Distinguish copied snapshot from dynamic/reference-derived reads.
   - If temporal behavior is not proven, say unknown.

3. **What code path can change this value after creation?**
   - Identify later mutation/override separately from initial origin.
   - Preserve source location and operation.

4. **Was this value directly copied or computed?**
   - Distinguish copy from derivation.
   - Retain all supported derivation inputs.

5. **What was the last observed source before the value was persisted or returned?**
   - Identify the last deterministically proven source/derivation before a supported terminal boundary.
   - Do not replace it with the earliest origin after transformations/overrides.

6. **What backend conditions and frontend conditions jointly determine whether an item is visible?**
   - Keep backend and frontend evidence separate.
   - Compose only when the same item/dataflow path is proven.

7. **How does a value travel through backend → DTO/projection → API → frontend composition?**
   - Explain every proven edge and preserve source locations.
   - Do not infer any cross-layer edge from matching names alone.

8. **If authority is incomplete, what lineage or causal evidence is still deterministically known?**
   - A downgraded business condition must not delete independent copy, derivation, mutation, DTO mapping or frontend-binding evidence.

These questions are the V0.4.7 acceptance surface. Raw fact existence alone is insufficient; portable knowledge must support the answer at PO abstraction level.

## Canonical lineage semantics

| Semantic | Required meaning |
| --- | --- |
| `copy` | A value is assigned directly from another value without a modeled computation changing it. |
| `snapshot` | A stored copied/derived value represents a point in time; later upstream changes do not alter it without another mutation. |
| `derivation` | A downstream value is computed from one or more proven inputs. |
| `reference/dynamic` | A downstream read resolves from upstream state at read time. |
| `override` | A later write supersedes a previously sourced value without erasing its original origin. |
| `mutation` | A code path writes downstream value/state after prior state existed. |

`copy` and `snapshot` are not synonyms. `override` is a later causal role and must not rewrite history.

### Temporal acceptance

For a stored scalar snapshot:

```text
ProductGroup.Price = 100
Product.Price      = ProductGroup.Price
Service.Price      = Product.Price
ProductGroup.Price = 120
```

existing `Product.Price` and `Service.Price` remain `100` unless another proven mutation copies the new value downstream.

A dynamic/reference read may report the changed upstream value only when that read-time dependency is proven.

## Same-name collision regression

A blocking negative includes unrelated values such as:

```text
Product.Price
Service.Price
Dto.Price

```

Acceptance:

- no lineage from normalized/equivalent names alone;
- casing, type name, route text or UI labels are not proof;
- deterministic source/dataflow evidence is required;
- explicit mapping creates only the proven edge; unrelated same-name nodes remain disconnected.


- frontend conditions retain their own source/provenance;
- joint observable visibility may be described only for the same proven item flow;
- unrelated predicates never join by textual similarity;
- observed-only backend evidence is never upgraded by frontend evidence.
