## Product-knowledge invariants

V0.4.7 extends the compiler without collapsing the permanent knowledge classes:

```text
business conditions
value lineage / provenance
mutation / causality
```

They can be connected in a PO-facing explanation, but they must remain distinct evidence classes.

The authority rule is unchanged:

```text
deterministically proven observable behavior
→ may become an authoritative product-behavior claim

deterministic implementation evidence without full authority
→ retain as lower-authority lineage / provenance / mutation / causal evidence

unsupported inference
→ do not invent
```

Conservative authority downgrade must never erase deterministic lower-authority evidence.

## V0.4.7 Product Owner acceptance questions

Generated portable knowledge must answer the following questions from evidence, or say explicitly that the answer is not proven:

1. **Where did this value originally come from?**
   - Identify the earliest deterministically proven source in the observed lineage.
   - Show each intermediate entity/property edge rather than jumping by property-name similarity.

2. **If the upstream value changes later, does the existing downstream value change automatically?**
   - Distinguish a copied snapshot from a dynamic/reference-derived value.
   - If temporal behavior is not proven, say so rather than assuming propagation.

3. **What code path can change this value after creation?**
   - Identify later mutation/override paths separately from the initial source.
   - Preserve the source location and operation that performs the change.

4. **Was this value directly copied or computed?**
   - Distinguish direct copy from derivation/computation.
   - For a derivation, retain the deterministically proven input dependencies.

5. **What was the last observed source before the value was persisted or returned?**
   - Trace to the terminal source/derivation step immediately before a proven persistence or return boundary.
   - Do not replace this with the earliest origin when the chain contains later transformations or overrides.

6. **What backend conditions and frontend conditions jointly determine whether an item is visible?**
   - Preserve backend selection/eligibility conditions and frontend visibility/filter conditions independently.
   - Compose them only when the same returned item/dataflow is proven across DTO/API/frontend boundaries.

7. **How does a value travel through backend → DTO/projection → API → frontend composition?**
   - Explain source entity/property, projection/DTO mapping, API output, frontend result binding/composition and final displayed/used field where each edge is proven.
   - Do not infer a cross-layer edge from matching names alone.

8. **If authority is incomplete, what lineage or causal evidence is still deterministically known?**
   - A downgraded business condition must not delete independently proven copy, derivation, mutation, override, DTO mapping or frontend-binding evidence.

These questions are the V0.4.7 acceptance surface. A change is not complete merely because new raw facts exist; the portable knowledge must support these answers at PO abstraction level with traceable evidence.

## Canonical lineage semantics

V0.4.7 must represent or otherwise preserve enough deterministic information to distinguish these edge semantics:

| Semantic | Required meaning |
| --- | --- |
| `copy` | A value is assigned directly from another value without a modeled computation changing it. |
| `snapshot` | A copied/derived value is stored at a point in time; later upstream changes do not automatically change the stored downstream value unless another mutation path executes. |
| `derivation` | A downstream value is computed from one or more proven inputs. |
| `reference/dynamic` | Reading the downstream value resolves from an upstream object/value at read time, so later upstream changes can affect later reads without a copy/update mutation. |
| `override` | A later write replaces or supersedes a previously sourced value. |
| `mutation` | A code path writes the downstream value/state after its prior state existed. |

`copy` and `snapshot` are not synonyms: copy describes the value-transfer mechanism; snapshot describes temporal behavior. An edge may therefore be both a direct `copy` and `snapshot`.

`override` is a causal role of a later mutation relative to earlier lineage. It must not erase the earlier origin.

## Required canonical acceptance fixture

The first V0.4.7 regression fixture must contain an equivalent of:

```text
ProductGroup.Price
    ↓ direct copy at Product creation
Product.Price
    ↓ direct copy at Service creation
Service.Price
```

For the canonical fixture, PKC must prove and render each edge separately:

```text
ProductGroup.Price → Product.Price
mechanism: copy
temporal semantics: snapshot

Product.Price → Service.Price
mechanism: copy
temporal semantics: snapshot
```

The fixture must also contain semantically distinct cases so the compiler cannot flatten every relationship into a generic "comes from":

```text
ProductGroup.Price → Service.CurrentGroupPrice
semantics: reference/dynamic

Service.Price + Service.Discount → Service.NetPrice
semantics: derivation

manual/update command → Service.Price
semantics: mutation + override
```

Equivalent names are allowed in tests, but production compiler behavior must be generic and symbol/dataflow based. No ProductGroup/Product/Service/Price special cases.

### Temporal acceptance behavior

Given a stored snapshot chain:

```text
ProductGroup.Price = 100
Product.Price      = ProductGroup.Price   // snapshot
Service.Price      = Product.Price        // snapshot
```

a later change:

```text
ProductGroup.Price = 120
```

must not be described as automatically changing existing `Product.Price` or `Service.Price` unless a separate proven update/mutation path copies the new value downstream.

By contrast, a getter or expression that resolves the upstream value at read time may be classified as `reference/dynamic` only when that dynamic dependency is proven.

## Same-name collision regression

A blocking negative regression must contain unrelated values with the same or equivalent property name:

```text
Product.Price
Service.Price
Dto.Price
Component.price
```

At least one fixture shape must contain all four without dataflow edges between some of them.

Acceptance:

- PKC must not create lineage merely because member names normalize to the same text.
- Casing differences such as `Price` vs `price` are not proof of identity.
- Type name, member name, route similarity or UI field label alone is insufficient.
- A lineage edge requires deterministic source/dataflow evidence.
- When one explicit mapping exists, only that proven edge is created; unrelated same-name nodes stay disconnected.

This is a blocker regression for any V0.4.7 lineage implementation.

## Backend → DTO → API → frontend acceptance chain

A cross-layer fixture must include an equivalent proven chain:

```text
Service.Price
→ ServiceDto.Price
→ controller/API response
→ frontend API result
→ component/view-model assignment
→ rendered/displayed price
```

The compiler must preserve edge provenance across layers and answer:

```text
What backend value feeds the displayed frontend price?
Was the DTO value copied or derived?
What was the last backend source before return?
What frontend binding/composition step consumed it?
```

No edge may be created from a property-name match without a proven projection, return/result binding or assignment path.

## Joint visibility acceptance

The cross-layer fixture must include both backend and frontend conditions for the same item path, for example:

```text
backend:
service.IsPublished && !service.Blocked

frontend:
item.price > 0 && matchesSelectedFilter(item)
```

The portable knowledge must be able to explain that visibility depends on two distinct layers:

```text
backend condition(s)
+ proven API/result path
+ frontend condition(s)
```

Requirements:

- backend conditions remain business-condition evidence with V0.4.6 authority rules;
- frontend conditions retain their own source and authority/provenance;
- PKC may describe a joint observable visibility constraint only when the same dataflow/item path is proven;
- unrelated backend and frontend predicates must never be joined because names or text look similar;
- an observed-only backend predicate remains observed-only and must not be upgraded by a frontend condition.

## Regression gates

### R7.1 — Direct cross-entity copy identity

A compile-valid C# fixture directly assigns one entity member to another.

Must prove:

```text
source symbol identity
target symbol identity
direct assignment/copy edge
source location
```

Must not use property-name equality as the edge proof.

### R7.2 — Multi-hop lineage reconstruction

For:

```text
ProductGroup.Price → Product.Price → Service.Price
```

the generated knowledge must preserve both edges and answer the full origin chain in order.

It must also answer the last observed source before `Service.Price` is persisted or returned.

### R7.3 — Same-name collision fail-closed

Unrelated `Product.Price`, `Service.Price`, `Dto.Price` and `Component.price` nodes must remain unconnected unless explicit deterministic dataflow exists.

False lineage is a blocker.

### R7.4 — Snapshot vs dynamic/reference semantics

Two semantically different fixtures must be distinguishable:

```text
stored assignment/copy
dynamic getter/reference-derived read
```

The PO answer to "does an upstream change automatically affect the existing downstream value?" must differ accordingly.

If the compiler cannot prove temporal semantics, it must say unknown rather than guess.

### R7.5 — Derived/computed value dependencies

A value computed from multiple inputs must be emitted as derivation, not direct copy.

The evidence must retain all supported input dependencies and the derived target.

### R7.6 — Later mutation and override causality

A later command/setter/update path that writes `Service.Price` must be retained separately from initial lineage.

The knowledge must answer:

```text
initial observed origin
later override/mutation path
resulting target
```

A later override must not rewrite history as if it were the original source.

### R7.7 — Persistence/return terminal-source proof

When a value is persisted or returned after intermediate copy/derivation/override steps, PKC must identify the last deterministically observed source/derivation step before that boundary.

Do not conflate "original origin" with "last source before output".

### R7.8 — DTO/projection mapping

A backend projection such as entity → DTO must connect only the exact proven source and target symbols.

Renames are allowed when the assignment proves them; same-name members without assignment are not.

### R7.9 — API result to frontend binding

A supported frontend fixture must prove API result/data binding into component/view-model state.

The cross-layer chain must retain backend and frontend source locations and must not rely on normalized member-name collision.

### R7.10 — Joint backend/frontend visibility

For the same proven item flow, portable knowledge must expose both backend selection/eligibility conditions and frontend visibility/filter conditions.

The answer must keep their authorities distinct while explaining their combined observable effect.

### R7.11 — Authority downgrade retains lineage/causality

Introduce a fixture where one business-condition authority path is intentionally incomplete or observed-only while deterministic lineage/mutation evidence exists.

Acceptance:

```text
no false authoritative business rule
lineage still present
mutation/override still present
DTO/frontend binding still present when independently proven
```

This is a permanent product-knowledge-contract gate.

### R7.12 — Portable knowledge rendering and parity

The canonical `knowledge/` pack must render lineage/causality at PO-readable abstraction level with source traceability.

`PKC_KNOWLEDGE.md` and `PKC_KNOWLEDGE.zip` must preserve the same critical lineage and authority meaning as the structured pack.

No raw `.pkc` or source-tree leakage may be introduced.

### R7.13 — Cross-benchmark regression

After each coherent V0.4.7 implementation checkpoint:

```text
focused V0.4.7 regressions
→ full C# tests
→ frontend tests when touched
→ Release build
→ PokeTrade known-answer
→ pinned Loren
→ Loren-main canary
→ pinned Jellyfin
→ portable parity/no-leak
```

CI remains final verification, not the edit/test loop.

## Version semantics

PKC uses several independent version domains. Do not mechanically align them.

### Roadmap milestone version

Examples:

```text
V0.4.6
V0.4.7
V0.5
```

This tracks roadmap/acceptance state in documentation. Advancing to V0.4.7 does not by itself change any serialized schema or package version.

### Tool/package version

Current accepted package:

```text
RuaDen.Pkc.Tool 0.4.3-preview.2
```

The package version is the distributable .NET tool version declared by `src/Pkc.Cli/Pkc.Cli.csproj`.

It changes only as an explicit packaging/release decision. This planning task does not bump it.

### Evidence/schema version

Serialized artifacts carry their own schema/contract identifiers. Current examples include:

```text
0.4.4-csharp-raw   C# combined raw evidence document
0.4.4              merged facts / baseline feature-candidate or product-feature document contracts
0.4.6              cross-stack feature-candidate contract
0.4.3-frontend     merged frontend evidence contract
```

These strings are schema identifiers, not roadmap progress counters.

A schema version changes only when the serialized contract or semantics for that artifact changes in a way that requires consumers/tests to distinguish the new contract. A V0.4.7 implementation may legitimately keep an existing schema version if its contract is unchanged.

Before any schema bump:

1. identify the exact serialized contract change;
2. define compatibility/migration expectations;
3. add schema/serialization regression coverage;
4. update readers/renderers/fixtures that depend on the contract;
5. document the reason for the schema change.

Do not mechanically change existing `0.4.4`, `0.4.4-csharp-raw`, `0.4.6` or other schema strings merely because V0.4.7 is current.
