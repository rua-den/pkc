## Product-knowledge invariants

V0.4.7 extends the compiler without collapsing the permanent knowledge classes:

```text
business conditions
value lineage / provenance
mutation / causality
```

They may be connected in a PO-facing explanation, but one must not be silently promoted into another.

Authority rule:

```text
deterministically proven observable behavior
→ may become an authoritative product-behavior claim

deterministic implementation evidence without full authority
→ retain as lower-authority lineage / provenance / mutation / causal evidence

unsupported inference
→ do not invent
```

Conservative authority downgrade must never erase deterministic lower-authority evidence.

## V0.4.7 Product Owner acceptance questions

Generated portable knowledge must answer these questions from evidence, or explicitly say the answer is not proven:

1. **Where did this value originally come from?**
2. **If the upstream value changes later, does the existing downstream value change automatically?**
3. **What code path can change this value after creation?**
4. **Was this value directly copied or computed?**
5. **What was the last observed source before the value was persisted or returned?**
6. **What backend conditions and frontend conditions jointly determine whether an item is visible?**
7. **How does a value travel through backend → DTO/projection → API → frontend composition?**
8. **If authority is incomplete, what lineage or causal evidence is still deterministically known?**

Raw fact existence alone is insufficient; portable knowledge must support the answer at PO abstraction level.

## Canonical lineage semantics

| Semantic | Required meaning |
| --- | --- |
| `copy` | A value is assigned directly from another value without a modeled computation changing it. |
| `snapshot` | A stored copied/derived value represents a point in time; later upstream changes do not alter it without another mutation. |
| `derivation` | A downstream value is computed from one or more proven inputs. |
| `reference/dynamic` | A downstream read resolves from upstream state at read time. |
| `override` | A later write supersedes a previously sourced value without erasing its original origin. |
| `mutation` | A code path writes downstream value/state after prior state existed. |

`copy` and `snapshot` are not synonyms. `override` is a later causal role and must not rewrite history.
