## Product-knowledge invariants

Keep business conditions, value lineage/provenance, mutation/causality, render authority and visibility authority distinct. Deterministically proven observable behavior may become authoritative product-behavior knowledge. Unsupported inference fails closed. Similar names are never sufficient proof.

## Product Owner acceptance questions

Portable knowledge must answer from evidence, or explicitly say the answer is not proven:

1. Where did this value originally come from?
2. If upstream changes later, does the existing downstream value change automatically?
3. What code path can change the value after creation?
4. Was it directly copied or computed?
5. What was the last observed source before persistence/return?
6. What backend and frontend conditions jointly determine visibility?
7. How does a value travel backend → projection/DTO → API → frontend → render?
8. What independently proven evidence survives when stronger authority is incomplete?
9. For a product workflow, who may perform it, what preconditions apply, what state changes, and what side effects occur?
10. Does a feature-level summary preserve the grounded rules present in its workflows?

Raw fact existence alone is insufficient.
