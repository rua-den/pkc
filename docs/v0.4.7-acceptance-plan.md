## Product-knowledge invariants

Keep business conditions, value lineage/provenance, mutation/causality, render authority and visibility authority distinct. Deterministically proven observable behavior may become authoritative product-behavior knowledge. Unsupported inference fails closed. Similar names are never sufficient proof.

Repository discovery adds another invariant once unlocked: expensive semantic analysis must not begin as an unbounded whole-root operation before PKC has a deterministic repository profile and inspectable ScanPlan.

## Product Owner acceptance questions

Portable knowledge must answer from evidence, or explicitly say the answer is not proven:

1. Where did this value originally come from?
2. If upstream changes later, does the existing downstream value change automatically?
3. What code path can change the value after creation?
4. Was it directly copied or computed?
5. What was the last observed source before persistence/return?
6. What backend and frontend conditions jointly determine visibility?
7. How does a value travel backend → projection/DTO → API → frontend → render?
8. What independently proven evidence survives when stronger authority is incomplete?
9. For a product workflow, who may perform it, what preconditions apply, what state changes, and what side effects occur?
10. Does a feature-level summary preserve the grounded rules present in its workflows?

Raw fact existence alone is insufficient.

## E0 — Repository Discovery + bounded run readiness — PREPARED / LOCKED

### Why E0 is first after D

A private mixed legacy enterprise repository demonstrated that the current product path can enter expensive whole-root semantic scanning before understanding repository shape. A manual run was observed consuming roughly 9 GB RAM before useful completion.

This is a product-acceptance blocker for the demo: a knowledge compiler that cannot practically produce its workspace on the target repository cannot be considered demo-ready, regardless of semantic benchmark quality.

The ~9 GB observation is not a universal threshold. E0 must first fix the structural cause: scope discovery and bounded execution.

### Required sequence once unlocked

```text
RD1 inventory + safe exclusion
→ RD2 application boundaries + ownership
→ RD3 vendor/custom frontend classification
→ RD4 runtime/plugin provenance
→ RD5 deterministic ScanPlan
→ RD6 scoped/bounded semantic execution
→ RD7 coverage + observability + plan-only inspection
→ RD8 private large-repo validation
```

Run these sequentially. No parallel production implementation across RD checkpoints.

### E0 required properties

E0 is PASS only when all applicable properties below are proven:

- repository inventory is deterministic and stable;
- discovery precedes expensive C#/frontend semantic scanning;
- strongly proven generated/restorable areas can be safely excluded;
- folder names such as `legacy`, `vendor`, `plugins`, `themes`, `Scripts`, `Content`, `old` are never exclusion authority by themselves;
- application/component boundaries and shared ownership are explicit;
- tests cannot create production authority;
- first-party runtime, first-party shared, third-party runtime, modified vendor, infrastructure, tests, generated/restorable and UNKNOWN can remain distinct;
- third-party runtime assets are indexed without deep-scanning internals;
- locally modified vendor code can receive a narrow first-party carve-out when evidence supports it;
- runtime/plugin edges carry deterministic provenance and confidence;
- ambiguous runtime/plugin/vendor/application shapes remain UNKNOWN/fail-closed;
- `scan-plan` is machine-readable, stable and inspectable;
- semantic scanners execute only planned scopes/application waves;
- TARGETED shared code is followed only from supported ownership/reachability;
- UNKNOWN areas are not silently discarded;
- coverage cannot claim READY when required planned areas are unsupported/omitted;
- discovery/plan artifacts do not copy source bodies or sensitive config values;
- users can inspect discovery/plan decisions before committing to expensive semantic execution through a plan-only/discovery path;
- progress/coverage numbers come from the actual plan;
- accepted semantic authority regressions continue to pass inside selected scopes;
- private large-repo validation shows materially better bounded behavior than the unbounded baseline and succeeds far enough to produce the intended `.pkc/workspace` for the approved demo repository.

### E0 evidence hierarchy

Prefer cheap deterministic evidence:

```text
filesystem/VCS shape
→ manifests/build/workspace metadata
→ bounded composition/runtime entry evidence
→ minimum targeted ambiguity resolution
```

Discovery must not become another recursive whole-source semantic pass.

### E0 privacy

Private validation reports may contain only sanitized aliases, approximate counts, classifications, resource deltas and failure categories. Do not copy proprietary source, exact internal names, endpoints, hosts, configuration values or credentials into PKC repository artifacts.
