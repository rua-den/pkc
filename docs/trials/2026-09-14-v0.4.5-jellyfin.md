Selection rationale:

- genuine long-lived open-source product repository, not created or modified for PKC;
- C# server backend and API fall inside PKC's currently supported backend surface;
- contains substantial product/system behavior rather than a toy/sample domain;
- controller/API organization differs materially from Loren's Minimal-API-first shape and from PokeTrade's controlled benchmark shape;
- intentionally selected as a demanding generalization target, not because existing PKC heuristics are known to handle it easily;
- no target-repository changes are permitted to make PKC succeed.

The pinned repository currently declares .NET SDK 10.0 and its own CI exercises `Jellyfin.sln`; the PKC trial therefore builds the pinned solution normally before compiling knowledge.

## Trial discipline

The first pass is knowledge-only.

Before freezing blind answers, do not inspect Jellyfin implementation details beyond repository metadata/build configuration needed to select and execute the benchmark.

Execution order:

```text
pin benchmark commit
→ build pinned source normally
→ compile PKC layered output
→ inspect analyzer/fallback provenance only for knowledge risk
→ verify structured/bundle/ZIP parity
→ review PKC_KNOWLEDGE.md knowledge-only
→ review structured knowledge/ only where deeper navigation is needed
→ freeze answers below
→ reopen Jellyfin source
→ cross-check every critical answer
→ classify findings
→ fix only generic compiler defects, regression-first
→ rerun PokeTrade + pinned Loren + Jellyfin after every compiler fix
→ request independent external review
```

V0.5 Azure DevOps remains locked throughout this trial.

## Blind knowledge-only questions

These questions are frozen before inspecting implementation behavior:

1. What observable product/system capabilities does the generated pack say the Jellyfin server exposes?
2. What authentication, authorization, user/session or access-control behavior is visible, including important success/failure outcomes?
3. How does the system expose or manage media libraries/items/metadata at a product level, and what important validations or failure paths are visible?
4. What playback/session/device-control behavior is observable, including side effects or integrations where present?
5. What administrative/system-management operations are visible, such as configuration, scheduled/background work, refresh/scan operations, or server lifecycle behavior?
6. Which externally meaningful state changes or mutations are visible, and under what permissions/guards?
7. Which important conditional behavior, validation, conflict/not-found/bad-request paths, or other failure semantics are visible?
8. Which integrations or external providers/services are visible from code-derived knowledge?
9. Can the product-level feature pages answer these questions without forcing the reader to reason from low-level helper/call-graph noise?
10. What does PKC explicitly not know because the repository lacks a supported frontend in this benchmark or because runtime/product-intent/delivery evidence has not been compiled?
