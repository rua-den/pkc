Selection rationale:

- genuine long-lived open-source product repository, not created or modified for PKC;
- C# server backend and API fall inside PKC's currently supported backend surface;
- contains substantial product/system behavior rather than a toy/sample domain;
- controller/API organization differs materially from Loren's Minimal-API-first shape and from PokeTrade's controlled benchmark shape;
- intentionally selected as a demanding generalization target, not because existing PKC heuristics are known to handle it easily;
- no target-repository changes are permitted to make PKC succeed.

The pinned repository currently declares .NET SDK 10.0 and its own CI exercises `Jellyfin.sln`; the PKC trial therefore builds the pinned solution normally before compiling knowledge.

## Trial discipline

The first pass is knowledge-only.

Before freezing blind answers, do not inspect Jellyfin implementation details beyond repository metadata/build configuration needed to select and execute the benchmark.

Execution order:

```text

```

## Frozen blind knowledge-only answers

The following answers were produced from `PKC_KNOWLEDGE.md` first and the generated structured `knowledge/` pack second. Jellyfin implementation source was not opened for this pass.

### 1. Observable capability surface

The pack presents Jellyfin primarily as a large server/API product with capability areas for users/authentication, sessions, playback/playstate, libraries/items/metadata, images, subtitles, lyrics, playlists, Live TV, media streaming/HLS, devices, SyncPlay, scheduled tasks, configuration, backup, system lifecycle, plugins/packages, remote provider lookup, search and supporting discovery APIs.

The generated index exposes 386 backend endpoints grouped into product-level feature areas and links those feature summaries to workflow-level evidence.

### 2. Authentication, authorization and access control

The pack shows multiple authentication paths: authenticate by user/id, authenticate by name, Quick Connect authentication, forgot-password and PIN flows. It also shows authorization policies on protected operations, including ordinary `Authorize`, `RequiresElevation`, download permission and local-access-or-elevated policy shapes.

Generated user/session workflows show important access constraints such as rejecting cross-user access unless the caller is an administrator, session-not-found behavior, token revocation after selected user/password/policy mutations, and Quick Connect unknown/disabled failure outcomes. User management includes create/delete/update/configuration/password/policy operations, while session capabilities include listing/reporting sessions and adding/removing users from a session.

A blind limitation is that some important authentication semantics are visible mainly in workflow flow/evidence rather than summarized under feature-level `Observed business rules`.

### 3. Media libraries, items and metadata

The pack exposes item/library discovery, media folders/physical paths, item counts/ancestors/collections, download/file access, theme media, virtual-library structure management, library refresh, item refresh, item update, metadata editor operations and remote metadata lookup/application.

Observed validations/failures include item/user not found, cross-user administrator checks, download eligibility checks, null media path rejection, and several media-info validation requirements. Library refresh calls the library manager validation path; item refresh queues provider refresh; remote lookup uses provider-manager search and can apply provider IDs before a full refresh.

The pack also shows mutations such as provider-ID replacement/update and repository updates after remote image operations.

### 4. Playback, sessions and device/control behavior

The generated knowledge shows playback start/progress/stop reporting, played/unplayed state, playback-session ping, session capability reporting, browse/display commands, play commands, playstate/system/general/message commands and user/session membership operations.

Observed playstate mutations include `Played`, `PlayCount`, `LastPlayedDate`, playback position and normalized play-method/session IDs. Playback progress/start/stop are routed through `ISessionManager`; stopped playback can kill transcoding jobs, and playback-session ping reaches the transcoding manager.

Session command workflows expose remote-control style behavior such as play, browse, message, general/system and playstate commands. Missing sessions are explicitly represented as not-found-style exceptions in several flows.

### 5. Administrative/system-management operations

The pack shows system ping/restart/shutdown, elevated configuration changes, branding configuration changes, named configuration replacement, scheduled-task start/stop/update, library refresh, package/plugin management and backup restore.

Examples of observed effects include `ISystemManager.Restart`, `ISystemManager.Shutdown`, scheduled-task execution, task-trigger updates, library validation/refresh, configuration save/replace calls and backup restore scheduling followed by server restart. Restore checks archive-file existence before scheduling restore/restart.

Most of these operations carry elevated authorization evidence.

### 6. Externally meaningful state changes and mutations

The pack exposes concrete mutations including user policy/password/token effects, played/unplayed state, play count and last-played date, session command fields, task triggers, branding configuration values, item/provider IDs and repository updates.

Important guards are also visible: ordinary authorization, elevation policies, cross-user administrator checks, resource existence checks, download permission/eligibility and operation-specific validation.

The feature/workflow split generally preserves the mutation evidence even when a feature summary does not promote every condition to a business rule.

### 7. Conditional, validation and failure semantics

The pack contains explicit not-found, forbidden/security, argument-validation and unauthorized conditions. Examples include missing session/item/user, forbidden cross-user access without administrator status, invalid/missing media-profile inputs, unsupported download, missing restore archive, invalid named configuration body and disabled/unknown Quick Connect states.

No broad claim is made that every possible runtime status code is compiled. The blind answer is limited to the failure paths actually surfaced by the generated pack.

### 8. Integrations and external providers/services

Code-derived knowledge shows provider-manager integrations for remote metadata searches, external-ID information, item refresh and remote image saving. It also exposes TMDb-related API surface, plugin/package repositories and plugin lifecycle operations, transcoding-manager interaction, Live TV capability areas and backup service integration.

The pack proves these collaborations exist in code; it does not establish business intent, external SLA/configuration or runtime availability for those integrations.

### 9. Product-level signal quality

Critical capability questions are answerable from the index plus feature pages, with workflow pages providing deeper proof. The hierarchy works: index → feature → workflow → evidence.

However, the benchmark is substantially larger than Loren: 504 Markdown files. Several feature pages still contain long `Observed capability flow` sections, and some important rules remain easier to understand only after opening workflows. This is a comprehension/noise risk to evaluate during source cross-check and independent review, but the first blind pass is not blocked from answering the critical questions.

### 10. Explicit unknowns

The pack is appropriately explicit that frontend/UI entry points and user interaction paths have not been analyzed for this benchmark. It also states that Azure DevOps delivery history/product intent, runtime UI confirmation and business approval are outside the compiled evidence.

Therefore the pack can describe observed server behavior and evidence, but it cannot claim actual UI steps, approved product requirements, delivery history, runtime configuration/availability or business intent unless explicitly grounded elsewhere.

## Blind-pass uncertainties to source-cross-check

These were recorded before opening Jellyfin implementation source and are not yet classified as compiler defects:

1. Several controller areas render unusually short backend entry paths, for example `/Enabled`, `/Restart`, `/Restore` and `/{pluginId}/{version}/Enable`. The source cross-check must determine whether controller/base-controller route prefixes are missing from PKC's composed route or whether those are genuinely the effective routes.
2. Feature-level summaries sometimes say `No grounded information available yet` for business rules even when linked workflow flow/evidence contains meaningful authorization, token-revocation or mutation semantics. Source cross-check must determine whether this is merely abstraction quality/noise or a material missing-behavior blocker.
3. The 504-file output is navigable but large. Independent review should challenge whether product-level feature pages remain sufficiently high-signal without depending on transitive call-graph detail.

The blind answers above are now frozen. Source inspection may correct them only by recording a finding; it must not rewrite the blind pass retroactively.
